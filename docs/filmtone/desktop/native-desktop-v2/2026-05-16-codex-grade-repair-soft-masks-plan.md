# Codex Grade Repair + Protective Soft Masks Plan

Date: 2026-05-16 JST
Status: Design memo, not an active implementation lane

## Summary

Codex 連携で目指す次の価値は、Filmtone を chat UI 付き編集アプリにすることではない。
Codex から Filmtone の headless automation API を呼び、Filmtone 側の解析・proof・補正エンジンで
肌転び、彩度暴れ、黒潰れ、黒浮き、ハイライト破綻を evidence-first に扱えるようにする。

ただし、最初の実装単位は repair ではない。

結論:

- できる。
- ただし「Codex に接続するだけ」ではできない。
- 最初は `Frame Metrics Harness` を作り、Filmtone がフレームを決定論的にサンプリングし、実測 metrics と issue candidates だけを返す。
- repair / soft mask / export は、signed preview と proof artifact が成立してから段階的に追加する。
- Codex は司令塔と説明役。画素解析、補正、proof、export は Filmtone の deterministic runtime が担当する。

## Product Thesis

Resolve / Lightroom / Premiere 的な manual mask UI を再現するのではなく、Filmtone は AI 前提の workflow に寄せる。

従来型:

```text
ユーザーが破綻を見つける
-> qualifier / mask / window / curve を手で作る
-> 補正する
-> 比較する
```

Filmtone AI-native:

```text
Filmtone が素材から evidence を作る
-> Codex が問題候補と限界を説明する
-> Filmtone が repair plan と proof を決定論的に作る
-> before / after / mask proof を出す
-> ユーザー承認後に batch export する
```

差別化の核は、破綻を `GradeIssue` として扱い、操作 UI ではなく evidence / plan / proof / export を製品 API 化すること。

## Target Problems

| Problem | Detection basis | First support level | Repair engine |
|---|---|---|---|
| ハイライト破綻 | high-luma stress, bright chroma stress, clipped-channel risk | Phase 1 metrics, Phase 3 repair | `Highlight Protect` |
| 彩度暴れ | chroma stress, gamut stress, channel edge stress | Phase 1 metrics, Phase 4 repair candidate | `Saturation Tamer` |
| 黒浮き | lifted black floor, low-luma density risk | Phase 1 metrics, later repair | `Black Anchor` |
| 黒潰れ | low-luma compression, recoverable shadow detail, noise-floor guard | Phase 1 metrics, later repair | `Shadow Protect` |
| 肌転び | skin candidate confidence, hue angle drift, luma/chroma guard | later metrics only after real fixtures | `Skin Stabilizer` |

`Skin Stabilizer` は誤爆リスクが高いので最後に追加する。Hue range だけで skin repair を ship しない。

最初の runtime repair は `Highlight Protect` に固定する。

理由:

- high-luma / clipped-channel / bright-chroma の metrics を比較的定義しやすい。
- before / after proof で副作用を確認しやすい。
- skin detection より false positive の被害が小さい。
- shadow repair より noise-floor 判定の難度が低い。

## MCP / CLI Shape

Codex に公開する tool は低レベル slider 操作ではなく、workflow 単位にする。

Phase 1 で公開する tool:

```text
analyze_grade_issues(paths, recursive?, samplePolicy?)
```

Later tools:

```text
preview_repair_plan(analysisId, targets?, strengthPolicy?)
render_repair_proof(planId, format?)
start_repair_batch(planId, overwrite?)
get_repair_job_status(jobId)
summarize_repair_job(jobId)
```

Do not expose:

- `set_saturation`
- `set_highlight`
- `set_mask_threshold`
- `set_skin_hue`
- live app window control
- in-app chat only surface

The API should eventually make Codex say:

```text
このフォルダを解析しました。ハイライト破綻の可能性が高い動画が2本あります。
今は実測 metrics に基づく候補で、フレーム内容の美的判断はしていません。
repair proof を作成してから、承認された plan だけを書き出します。
```

## Frame Metrics Harness

Phase 1 の本体は `Frame Metrics Harness`。
repair ではなく、解析が製品として信用できる最小基盤を作る。

Sampling policy:

```text
schemaVersion: "filmtone-analysis-v1"
sampleUnit: "seconds"
maxSamplesPerVideo: 24
minSamplesPerVideo: 5
includeFirstFrame: false
includeLastFrame: false
sceneCutDetection: false
selection: deterministic time-stratified samples
```

Frame decode and color rules:

```text
decode with native media stack
apply source input transform / source profile normalization
measure in working linear or documented working RGB
record display size, pixel format, transfer hint, color primaries if available
do not use creative LUT output for initial issue detection
```

Metrics:

```text
lumaHistogramSummary
rgbChannelStressSummary
brightChromaStressSummary
gamutStressSummary
shadowDensitySummary
blackFloorSummary
sampleQualityWarnings[]
```

Phase 1 issue eligibility:

```text
highlightBreak: eligible
saturationRunaway: eligible
blackFloat: metrics only, candidate allowed when confidence is high
blackCrush: metrics only until recoverable-detail fixture exists
skinShift: not eligible until real skin fixtures and skin candidate confidence exist
```

Performance budget:

```text
small folder: <= 12 videos, <= 24 samples each
large folder: cap samples and return truncation warnings
still sources: inspect and measure if supported, but do not repair/export in this lane
corrupt media: return per-source warning, continue analysis
```

## Core Data Contracts

All contracts are versioned JSON. The text below is the required shape, not a final Swift type name.

### `AnalysisManifest`

Generated by Filmtone, consumed by Codex.

```text
schemaVersion: "filmtone-analysis-v1"
analysisId
createdAt
expiresAt
toolVersion
sources[]
samplePolicy
sampledFrames[]
sourceMetadata[]
lookContext
exportContext
metricsSummary
issues[]
analysisLimits
warnings[]
```

`sampledFrames[]` uses seconds as the stable external unit. Internal Swift code may use `CMTime`, but JSON must serialize seconds plus optional frame index when known.

### `GradeIssue`

```text
issueId
sourceId
sourcePath
type: highlightBreak | saturationRunaway | blackFloat | blackCrush | skinShift
supportLevel: measured | candidate | metricsOnly | cannotConclude
confidence: 0.0..1.0
severity: 0.0..1.0
affectedFrameRanges[]
affectedPixelRatio
evidence[]
cannotConcludeReason?
```

`confidence` means confidence that the issue exists.
`severity` means estimated visual risk if the issue is left unchanged.

### `RepairPlan`

Generated only after `AnalysisManifest` exists.

```text
schemaVersion: "filmtone-repair-plan-v1"
planId
analysisId
createdAt
expiresAt
targets[]
repairPatch
expectedSideEffects[]
proofRequired: true
proofOutputs[]
exportProfiles[]
signature
warnings[]
```

### `RepairProof`

Proof is required before destructive or long-running export.

```text
schemaVersion: "filmtone-repair-proof-v1"
planId
proofId
createdAt
expiresAt
contactSheetPath
maskPreviewPaths[]
beforeAfterPreviewPaths[]
metricDeltas
summary
limits
signature
```

`metricDeltas` is required before Codex can say things like "黒は持ち上げていません" or "平均輝度変化は小さい"。

## Analysis Limits

Codex must not visually claim what Filmtone has not measured or shown.

`analysisLimits` should be explicit:

```text
metadata-only
metrics-only
proof-artifact-generated
thumbnail-visible-to-codex
full-local-frame-analysis
```

Current Codex MVP is effectively `metadata-only`: it can inspect source metadata and batch/export context, but cannot assert actual skin shift, clipping, or mask regions.

Grade issue candidates require at least `metrics-only`.

Claims like "肌が緑に転んでいる" require:

- deterministic skin candidate + hue drift evidence, and
- real fixture validation, and
- either proof artifact reviewed by the user or explicit permission for Codex to inspect thumbnails.

By default, proof images stay local and are described to Codex through metrics and paths only.

## Security And Proof Safety

Repair workflows create media artifacts. They must inherit the current MCP security model rather than creating a parallel path policy.

Required rules:

- `analysisId`, `planId`, and `proofId` expire.
- `RepairPlan` and `RepairProof` are signed or otherwise bound to the originating analysis.
- `start_repair_batch` accepts only a valid, previewed, unexpired `planId`.
- Default `overwrite` is `false`.
- Output and proof paths must pass the same allowed-root policy as existing MCP batch jobs.
- Contact sheets and mask previews are local artifacts; do not upload or remote-process by default.
- Codex does not receive frame pixels by default. It receives metrics, warnings, and local artifact paths.
- Proof artifacts should have a cleanup/retention policy.

## Runtime Placement

Protective repair should live before the creative LUT / final print shaping, so the repair acts on source-relative or working RGB evidence instead of trying to undo already-baked output damage.

However, Phase 1 does not change runtime output.

Phase 3 proposed order:

```text
source input transform / source profile normalization
-> protective repair stage
   -> Highlight Protect, first
   -> Saturation Tamer, later
   -> Shadow Balance, later
      -> Black Anchor or Shadow Protect, mutually exclusive
   -> Skin Stabilizer, much later
-> existing Filmtone base grade / compression / optics
-> creative LUT
-> print stage
```

The export path needs an explicit `repairPatch` carrier before runtime repair ships.
Current batch export cannot silently infer repair from global `gradeParams`.

For the future Basic control layer, keep the contract compact:

```text
Shadow Balance       -100..+100
Saturation Protect      0..100
Highlight Protect       0..100
Skin Protect            later / advanced only
```

`Shadow Balance` is bipolar:

- negative means Black Anchor for black float
- positive means Shadow Protect for black crush
- zero means no shadow-direction protection

Do not apply Black Anchor and Shadow Protect sequentially in the same basic path.

## Sidecar Metadata

Sidecar support should be additive and versioned.

Proposed block:

```text
repair:
  schemaVersion: "filmtone-repair-v1"
  analysisId
  planId
  proofId?
  analysisLimits
  appliedRepairs[]
  issueSummary[]
  proofHash?
  warnings[]
```

Do not store proof images inside the sidecar. Store stable identifiers, local paths when useful, and hashes for auditability.

## Implementation Phases

### Phase 1 — Frame Metrics Harness

Goal: detect and report likely grade issues without changing output.

Scope:

- Add deterministic frame sampling.
- Add source-normalized metrics summaries.
- Add `AnalysisManifest` / `GradeIssue` JSON.
- Add `analyze_grade_issues`.
- Return `highlightBreak` and `saturationRunaway` issue candidates.
- Return black float / black crush metrics, but keep repair disabled.
- Do not generate repair plans.
- Do not generate masks.
- Do not change export output.

Minimum fixture set:

```text
highlight-break-log
sat-runaway-log
black-float-log
black-crush-log
neutral-no-issue-log
corrupt-media
large-folder-cap
skin-shift-log, optional evidence only
```

### Phase 2 — Signed Repair Preview And Proof

Goal: generate repair plans and proof artifacts, still without final batch execution.

- Add `preview_repair_plan`.
- Add `render_repair_proof`.
- Generate before / after / mask preview contact sheets.
- Add signed `planId` and `proofId`.
- Refuse unknown, stale, or tampered analysis IDs.
- Keep all plans reversible and serializable.

### Phase 3 — Highlight Protect Runtime Repair

Goal: connect exactly one low-risk repair to proof and export.

First runtime repair:

```text
Highlight Protect
```

Requirements:

- `repairPatch` carrier in CLI and export request.
- protective repair stage before creative LUT / print stage.
- metric delta proof for highlight reduction.
- guard for midtone and black-floor drift.
- sidecar repair metadata.
- proof-required export gate.

### Phase 4 — Repair Batch

Goal: Codex can run approved repair plans through headless export.

- Add `start_repair_batch`.
- Preserve preview-first and proof-first rule.
- Default `overwrite: false`.
- Default `continueOnError: true`.
- Record per-source failures in summary.
- Write sidecar repair metadata for auditability.

### Phase 5 — Saturation Tamer

Goal: reduce saturation/gamut stress without flattening neutral midtones.

Requirements:

- synthetic chroma ramp fixture.
- bright chroma fixture.
- neutral midtone unaffected check.
- proof metric for chroma stress reduction.
- guard against accidental skin desaturation.

### Phase 6 — Shadow Balance

Goal: handle black float and black crush only after fixture proof is strong.

Rules:

- Black Anchor and Shadow Protect are mutually exclusive in the basic path.
- Shadow Protect requires recoverable-detail evidence.
- Do not lift noise floor to "fix" black crush.

### Phase 7 — Skin Stabilizer

Goal: target real skin shift without turning warm non-skin objects into false positives.

Requirements:

- real `skin-shift-log` fixture set.
- skin candidate confidence.
- hue-angle guard.
- luma/chroma guard.
- low default correction amount.
- mask proof required.

Do not ship skin repair from hue range alone.

## User Experience

Codex conversation should be short and action-oriented:

```text
User:
このフォルダを見て、肌転び・彩度暴れ・黒潰れ・ハイライト破綻だけ自然に直してSNS用に書き出して。

Codex:
解析しました。現時点では実測 metrics に基づく候補だけを返しています。
3本中2本にハイライト破綻の可能性、1本に彩度暴れの可能性があります。
肌転びはこの解析レベルでは判断しません。
repair proof を作成して確認します。
```

After proof:

```text
Codex:
before/after と mask proof を作成しました。
metric delta では、対象ハイライトの stress が下がり、黒レベルの変化は許容範囲内です。
承認されれば social1080 で batch export します。
```

Codex must avoid claims that are not backed by metrics or proof.

## Non-Goals

- Manual brush / Power Window UI in the first phase.
- Resolve node graph parity.
- AI hallucinated visual diagnosis without evidence.
- In-app chat as the primary product surface.
- Low-level control tools exposed directly to Codex.
- Cloud upload or remote frame processing by default.
- Public release claims before real-frame proof exists.
- Skin repair before real fixture proof exists.
- Runtime export modification in Phase 1.

## Open Decisions

1. Whether proof artifacts should be still PNG contact sheets, short MP4 previews, or both.
2. Exact retention/cleanup policy for proof artifacts.
3. Whether visual frame thumbnails can be passed to Codex by default, or only after explicit user permission.
4. Whether Skin Stabilizer should use deterministic color heuristics only, Vision / face detection, or a hybrid.
5. Whether Phase 1 metrics should live in AutomationCLI only first, or be extracted into a reusable Swift core module immediately.

Resolved decisions:

- First implementation lane is `Frame Metrics Harness`, not repair.
- First runtime repair is `Highlight Protect`.
- Repair metadata belongs in an additive `repair` sidecar block.
- Repair export requires signed preview/proof before execution.
