## Current Conclusion

Quality export の速度最適化として、読み込み時の quality mezzanine cache 生成を追うのは筋が悪い。

今回の実測では `decode` は 2.0 秒しかなく、総 export 159.8 秒のうち `render` が 149.2 秒、93.4% を占めた。仮に cache で decode を完全に 0 秒にしても短縮余地は最大 2 秒程度。次にやるべきは mezzanine/cache ではなく `ciContext.render(...)` の中に入っている grade/render pipeline の sub-stage 分解。

注意: これは **Quality export 速度改善** の話。既存の preview-grade mezzanine cache が Speed/preview の UX に効いている可能性は別問題なので、削除判断は別途行う。

## Interpretation

`render` dominates. `decode` is not the bottleneck.

Stage share:

| Stage | Time | Share |
|---|---:|---:|
| total export | 159.8s | 100% |
| render | 149.2s | 93.4% |
| build graph | 5.8s | 3.6% |
| decode | 2.0s | 1.3% |
| append | 0.8s | 0.5% |
| residual | 1.8s | 1.2% |
| writer finish | 0.013s | ~0% |

Therefore:

- Quality mezzanine cache generation at import time is not worth pursuing for this bottleneck.
- A decode-oriented cache cannot materially improve this 159.8s export.
- The next investigation must split `renderMs` by image-processing stage.

## Next Task

Add sub-stage timing inside `applyGrade` / motion:

- `InputLut`
- `BaseGrade`
- `ToneCompression`
- `EdgeOptics`
- `GlowFamily`
- `Vignette`
- `Grain`
- `CreativeLut`
- `PrintStage`
- `Motion`

Recommended implementation:

1. Extend `FilmtoneExportPerformanceMetrics` with render sub-stage counters.
2. Add a lightweight helper around each stage in `applyGrade(to:timeSeconds:)`.
3. Because Core Image is lazy, timing just the CIImage construction will not measure GPU time. To measure actual sub-stage GPU cost, the safest first pass is:
   - keep current macro `render` timing as ground truth
   - add a temporary profile mode that forces `ciContext.render` after selected sub-stage boundaries into a scratch pixel buffer at output size
   - run one representative export/profile pass
   - compare forced-render stage totals against macro render time
4. Avoid shipping forced sub-stage renders in production path. Gate with a private profiling flag or keep it as temporary branch instrumentation.

Important caveat:

Naively wrapping `applyInputLutStage(...)` etc. with wall-clock timers only measures CIImage graph construction, not GPU execution. It will likely show low numbers and mislead. The next chat must account for Core Image laziness.

## Do Not Do Next

- Do not spend more time re-enabling quality mezzanine cache before render sub-stage split.
- Do not assume `buildGraphMs` is the expensive effect; it is CIImage graph construction and is only 3.6%.
- Do not optimize H.264 writer settings first; writer finish / append are negligible in this run.
- Do not remove preview-grade cache broadly without checking Speed/preview behavior.
