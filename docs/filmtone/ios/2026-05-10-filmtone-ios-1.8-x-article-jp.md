Filmtone の iOS 版、1.8 がようやく App Store に出ました。

今回はけっこう中身を入れ替えています。せっかくなので、なぜそうしたのかを少しだけ書いておきます。撮影まわりを触っている iOS 開発者の方や、ふだん DaVinci で色を作っているカラリストの方に、ちょっと興味を持ってもらえたら嬉しいです。

(技術的な細部はあとで自分で読み返して「あれ、ちょっと違ったかも」となる箇所が出るかもしれません。気づいたら静かに直していきます。明らかな間違いがあれば教えてもらえると助かります。)

## まず Filmtone って何のアプリでしたっけ

Filmtone はフィルム調のカラグレツールで、**Desktop(macOS)版と iOS 版の 2 つの版**を出しています。今回アップデートしたのは、そのうちの **iOS 側** です。

ざっくり言うと、

- **Filmtone Desktop**: macOS のアプリ。クラウドを使わずに、手元の素材を Mac で仕上げて書き出すための版。現在も公開中です
- **Filmtone iOS**: iPhone のカメラで撮るところから、Look を当てて書き出すところまでを一本でやる方向で作っている版。1.8 はこちらの大きめのアップデート

という感じ、というつもりで作っています(細かい守備範囲はバージョンによって動きます)。

Filmtone の中身でいちばん大事にしているのは、**Desktop と iOS で同じ色のしくみを通している** ところです。色変換・モーションブラー・露出計算は TypeScript に集約してあって、そこから WebGL / WebGPU / Swift にコードを機械生成して、最後に `verify:swift-contract` で「両側で同じ数値が出ているか」を検証する、という構成にしてあります(規律で揃えるんじゃなく、構造で揃える、というつもり)。

なので **Desktop で作った Look は、iPhone でも同じに当たるはず** です。このあたりは別の記事[^cross-platform]に書いたのでそちらに譲ります。

[^cross-platform]: [TypeScript の色変換数学から Swift コードを機械生成する — Filmtone のクロスプラットフォーム色一致パイプライン](https://www.chibatakumi.studio/journal/filmtone-cross-platform-color-parity)(journal の既存記事)

それともうひとつ、Filmtone は **どのカメラで撮ったソースでも扱える方向を目指している** アプリです。SHOT ON iPhone を売りにしているわけではないつもりで、Sony でも Canon でも、なんなら家にあった古いコンデジでもいい。Filmtone がやろうとしているのは、その**後ろ側**——「素材が何であれ、仕上げをちゃんと iPhone(または Mac)で完結させる」ほうです。

iOS 1.8 は、その「iPhone で完結」の側を、撮影から書き出しまで一本に通せる形にしたかった、というのが今回のテーマです。

## 撮影画面、ぜんぶ作り直しました

ここからは少し開発の話。

旧バージョンの撮影画面、じつは React + Capacitor の薄い殻の上で動いていました。

これ、なんとなくそうなっていたわけではなくて、Filmtone の core renderer は最初に **WebGPU(と WebGL fallback)** で組んであって、その同じパイプを iOS でも回したい、というのが当初の発想だったんです。React + Capacitor を被せれば、Web 側で書いた WebGPU レンダラーをそのまま iPhone 上でも動かせる。Desktop との色一致もそこに乗っかる。最初の選択としては、それなりに筋があったつもりでいました。

ただ、撮影画面で Live Look(撮影中に LUT をかけたプレビュー)を載せていくにつれて、Capacitor 越しの WebGPU 経路ではどうしてもパフォーマンスが伸びきらない、というのが見えてきまして。1.8 ではここをまるごとやめる方向にしました。

撮影セッションは AVFoundation でゼロから組み直して、画面はネイティブの SwiftUI に置き換えています。Capacitor 側のコードは、自分が見えている範囲ではほぼ消したつもりです(さよなら)。色のロジック側は、前述のとおり TypeScript の source-of-truth から Swift コードを機械生成する経路を通しているので、レンダリング層が native に降りても **Desktop と同じ色のしくみは保ったまま** にしてあります(つもりです)。

手元の iPhone 17 Pro で確認しているかぎりでは、**4K24 の ProRes、Apple Log 2 のまま** 入ってきています(他の機種・OS バージョンでは挙動が変わる可能性があります)。Log 2 のまま編集側に渡せると、あとから色を作るときに少し余裕が出てくれるはず、というのが今回の狙いです。Rec.709 化されてから受け取るのとは、たぶん違ってくると思います。

それと、撮影フローも変えました。1 本撮り終えても、いきなり編集画面に飛ばないようにしてあります。そのまま次のテイクに進めて、あとからテイクの一覧を大きいプレビューで見比べてから、編集に持っていくテイクを選ぶ、という形です。テイクをポンポン重ねていく感覚に近い、はず。

## 録画中と書き出しを「分けた」、という話

これは個人的にいちばん書きたかった設計の話です。

撮影中って、よく考えるとピクセルまで完璧な絵は要らないんですよね。**色の当たりが合っているか**、**フレーミングが見えているか**、その 2 つが見えていればたぶん充分。なのにフル品質のレンダラーをそのまま回してしまうと、Look と手ぶれ補正を両方 ON にしたあたりで端末が悲鳴を上げ始めます。

なので 1.8 では、

- **撮影中**: 軽量レンダラー(色の当たりが見える程度)
- **書き出し**: フル品質レンダラー(これまでどおり)

という二段構成にしました。要するに「現場で見るための絵」と「最後に書き出す絵」を別物として扱う、というつもりの設計です。

ぱっと見では分かりづらい変更ですが、自分の手元で試したかぎりでは、撮影中の発熱とフレーム落ちが減って、**Look + 手ぶれ補正を両方 ON にしたまま長く回せる** ようになっていると思います。端末や条件で差は出るはずなので、あくまで僕の体感、ということで読んでもらえたら。

## カラリストの方に — `.cube` を読み込めます

ここからは色の話。

撮影画面で、**カスタムの `.cube` LUT を読み込めるようにしました**。Filmtone 側に元から入っている `Stone` / `Urban` と、新しく追加した `Noir`、それに自分で持ち込んだ LUT を、同じ並びで選べる形にしてあります。

ひとつ、お節介な機能を入れています。**Log → Rec.709 の変換が組み込まれていそうな LUT を読み込んだときに、画面上で軽く注意を出すようにしました**。

ここで言いたい LUT は、ACES の IDT / ODT のような純技術変換だけじゃなくて、**現場でいう transform LUT / show LUT、つまり「Log → Rec.709 の conversion と、その上の creative look が一本に焼き込まれている display LUT」も含みます**(この記事ではまとめて「Log 変換を含む LUT」と書きます)。実務上はむしろこの hybrid のほうが流通量は多い、という認識でいます。

事情としては、Filmtone 側で **Apple Log 2 → 表示空間の変換は先にこちらで済ませている** ので、その上から「Log 変換を含む LUT」を Look として乗せてしまうと、変換が二重にかかって色がだいぶ破綻してしまうんです。やったことある人はわかると思うんですが、現場で「あれっ?」となるやつです。

なので「この LUT、Log 変換が入っているように見えますよ」と、画面上でやんわり伝えるようにしてあります(判定はファイル名・タイトルのキーワードに加えて、LUT の neutral ramp の形状も見る三本立てですが、完璧ではないので誤検知・見逃しはあるはずです。そこはごめんなさい)。

ただし、**読み込み自体は止めないようにしてあります**。判断は使う側に残したいので。「警告は出るけど、それでも乗せたい」が選べる側に立てておきたいなと。

それから、撮影画面で選んだ Look や LUT は、**そのまま編集と書き出しまで引き継がれるように作っています**。撮影で当てた色を、編集で付け直したり、書き出しで再選択したりしなくて済むはずです。Look の二重指定が起きないように、選択は一本のレールに乗せてあります(もしどこかで切れていたら、それはバグです。教えてください)。

## 現場で壊れにくくしたこと

最後は、地味なんだけど効くやつをまとめて。

- **縦横の向きの扱い** を整理して、撮影中に不意に画面が回ってしまう挙動が出にくくなっている、はずです
- **保存容量が少なくなってきたとき** に警告が出ます(撮影が止まる前に気づけるように)
- **撮影パッケージ(テイク本体 + メタ情報 + サイドカー)の永続化** を強くしました

外部 SSD に書き出しながら長く回す現場でも、パッケージが壊れにくくなっている、と思います。長尺収録のときに、いちばん怖いのは「撮ったはずなのに開けない」ですからね。ここはまだ詰めきれていない部分もあるはずなので、何かあれば issue でも DM でも連絡もらえると助かります。

## というわけで

Filmtone iOS 1.8、無事 App Store に出ました。

派手な新機能というより、**「撮影 → 編集 → 書き出し」を、iOS 側でも素直に一本の道として通せるように作り直した** 回、というつもりです(Desktop 側はまた別の動きをしているので、それはそれでまたいずれ書きます)。

開発者の方はネイティブ移行と二段レンダラーの分業のあたりを、カラリストの方は `.cube` 周りと Look の引き継ぎのあたりを、よければ見てみてください。

触っていただけると嬉しいです。気づいたことがあれば、優しく教えてもらえると助かります。
