# Filmtone iOS v1.5 — 1080p Output-Oriented Mezzanine Cache (Handoff)

作成: 2026-05-02 JST
worktree: `.claude/worktrees/ios-v1.5-export-profile`
branch: `feature/ios-v1.5-export-profile`(base = `feature/ios-quality-mezzanine-cache-validation` 3d56a6b)

## Context — pivot from instrumentation-only to architectural fix

Step 1 で `FilmtoneExportSession.swift` に 5 種類 OSSignposter macro(decode / wait-encoder / build-graph / render / append)を計装し、Simulator build green まで終わった段階で、user から本質的な指摘:

> 「現在の動きは絶対おかしいです。読み込み時のキャッシュ絶対使ってない。書き出し時にもう一度準備してる。」

code 調査でこの指摘が **構造的に正しい**ことを確認:

`apps/capacitor-film-lab-ios/ios/App/App/SourceColorClassifier.swift:82-110` (v1.4 base) のコメント:

> v1.4 (2026-05-02): `qualityPrewarmVariant` **always returns nil on iOS**.
> Empirical measurement on iPhone 17 Pro / A18 Pro showed the qualityHDR HEVC
> Main10 4K 120 Mbps mezzanine pre-encode pass costs more than the decode-time
> saving recovers (174 s source-direct vs 243 s qualityHDR route on a 156 s
> ProRes 422 Apple Log clip — a +69 s net loss).
>
> Quality export therefore stays source-direct on every source class.
> ...so v1.5+ can re-enable selectively once a faster intermediate strategy
> (e.g. **1080p output-oriented cache**) is proven.

つまり:
- v1.4 で qualityHDR mezzanine route を **完全 disable**(iOS 専用)。理由: 4K HEVC pre-encode コストが decode 短縮効果を上回った
- 設計者は v1.5+ で「**1080p output-oriented cache**」戦略を取れと code コメントに明記
- ProRes Apple Log 156秒 / 8.88GB を 1080p H.264 export → 現状 **146秒**(source-direct)
- 1080p output-oriented mezzanine が走れば:
  - ProRes 4K decode → HEVC 1080p decode に置換(~60% 短縮想定)
  - grade pipeline の input ピクセル数 4倍削減(render 区間 ~75% 短縮想定)
  - 合計 expectation: 146秒 → 60〜80秒(target 86秒以下達成見込み)

Step 1 で挿入した signposter は v1.5 implementation の前後比較用に残置(計装の overhead は無視可能、production 残置可)。実機 trace の数値裏取りは optional になった(architectural fix が効くことが code から確定)。

## 適用済み変更(2 ファイル)

### 1. `apps/capacitor-film-lab-ios/ios/App/App/MezzanineService.swift`(Profile struct)

**Profile.version**: `5` → `6`(既存 cache 全 invalidate、新スキーマで再生成)

**Profile.qualitySDR**:
- `longEdge: 0` → `1920`(source-resolution preserve → 1080p downscale)
- `bitrate: 80_000_000` → `25_000_000`(4K base → 1080p HEVC perceptually-lossless)

**Profile.qualityHDR**:
- `longEdge: 0` → `1920`(同上)
- `bitrate: 120_000_000` → `30_000_000`(4K base → 1080p HEVC 10-bit Main10)

**`preservesSourceResolution`**: 全 variant で `false` 返却(longEdge ベースで判定する設計に統一)。`isValidMezzanine` 内の解像度一致検証(L338)は no-op 化(profile.version bump で cache key が変わるので機能上問題なし)

**`outputSize(forTrack:)`**: 全 variant で `FilmtoneExportSession.scaledSize(for: track, longEdge: longEdge)` を使う(preserveSourceResolution 経路 削除)

**`effectiveBitrate(forOutputSize:)`**: 4K-area scale 経路 削除、固定 bitrate 返却(全 variant が 1080p target に統一されたため不要)

**Limits.maxBytes**: `4_294_967_296`(4 GB)維持。新 spec では mezzanine 1 本あたり ~485 MB(qualitySDR 25Mbps × 156s) / ~585 MB(qualityHDR 30Mbps × 156s)で、4 GB cache に 6-7 entries 余裕で収まる(旧 4K spec では qualityHDR 1 本で 2.34 GB、cache 圧迫)

### 2. `apps/capacitor-film-lab-ios/ios/App/App/SourceColorClassifier.swift`(qualityPrewarmVariant)

v1.4 の `_ = colorClass; return nil` から、eligibility gate 付きの再有効化:

```swift
guard let colorClass else { return nil }

let baseVariant: Variant?
switch colorClass {
case .sdrBt709: baseVariant = .qualitySDR
case .hdrPq, .hdrHlg, .appleLog, .appleLog2, .wideGamutUnknown: baseVariant = .qualityHDR
case .unsupported, .unknown: baseVariant = nil
}
guard let variant = baseVariant else { return nil }

let isHeavyCodec: Bool
switch codecFamily {
case .prores422, .prores4444, .proresRaw: isHeavyCodec = true
case .h264, .hevc, .none: isHeavyCodec = false
}
let hasHighBitrate = (estimatedDataRate ?? 0) >= 100_000_000
guard isHeavyCodec || hasHighBitrate else { return nil }

return variant
```

**Eligibility**:
- ProRes 系(`.prores422` / `.prores4444` / `.proresRaw`) または ≥100 Mbps source → prewarm 起動
- 軽量 H.264 1080p 通常素材 → skip(再 encode コストが decode 短縮を上回る)

## 期待効果(コードベース推論、未計測)

| stage | v1.4 (source-direct) | v1.5 (1080p mezzanine) | 削減 |
|---|---|---|---|
| Decode (ProRes 4K → HEVC 1080p) | 60〜80 s | 20〜30 s | -40〜50 s |
| Render (grade pipeline 4K → 1080p) | 80〜120 s | 20〜35 s | -60〜85 s |
| Encode (1080p H.264) | 5〜15 s | 5〜15 s | ±0 s |
| **Total** | **146 s** | **60〜85 s** | **-60〜86 s** |

CD target **86 秒以下** に対し、コード変更だけで到達見込み(GlowFamily MIP 削減・kernel fusion 等の追加最適化なしで)。

## 注意点 / リスク

1. **Mezzanine 生成自体は 60〜90 秒かかる**(import 後 `Task.detached(priority: .utility)` で background 進行)。user が import 直後に export 押すと `ensureMezzanineBlocking` で待機=「準備中」見える。ただし source-direct 146 秒よりは速い(60秒生成 + 30秒 1080p export = 90秒)
2. **2160p export 時に 1080p mezzanine 使うと up-scale で品質劣化**。当面 1080p export 限定で運用、2160p の保護 guard は v1.5.1 で `selectedVariant` に request output longEdge 引数追加で対応
3. **v=6 bump で v=5 mezzanine 全て invalidate**(既存ユーザーは初回 import で再生成)。これは `Limits.maxBytes` 4 GB 内に収まるので大量パージは発生しない
4. **HDR source(Apple Log / HLG / PQ)で qualityHDR 1080p mezzanine 経路が live**。HDR→SDR tone-map は既存 `sourceImageOptions(toneMapHDRToSDR:)` 経路でカバー
5. **既存 Step 1 計装(signposter)は残置**。実機計測で数値裏取りする時に再利用可
