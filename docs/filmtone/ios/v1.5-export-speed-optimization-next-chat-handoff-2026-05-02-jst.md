- 元の 174秒 source-direct より 28秒速い理由は F7 で Connect package の 8GB source.mov copy を停止したことと、disk contention の消失

## v1.5 で解くべき問題

ユーザー判定: 「最初(Photos からの source 取り込み)で 1分以上待っているので、export を最低 60秒短縮できないと cache 戦略を組む意味がない」。

つまり target は **146秒 → 86秒以下**、35〜40% の高速化。

### 推定: 146秒の内訳(未計測、要 Instruments 検証)

| stage | 推定コスト | 備考 |
|---|---|---|
| ProRes 422 hardware decode (4K30, 156秒) | 5〜10秒 | hwaccel が支配、CPU bound にはならない |
| Color grade pipeline (CIImage / FilmtoneColorPipeline) | 60〜80秒 | LUT × optics × glow × depth 等の CIKernel chain、CIContext.render は同期 |
| 1080p H.264 encode (3744 frames) | 30〜40秒 | iPhone 17 Pro の H.264 encoder ~150fps スループット相当 |
| Connect package companion(現在は無効) | 0秒 | F7 で skip |
| その他(probe / sidecar / saveToPhotos 等) | 5〜10秒 | |

→ 支配コストは color grade。decode を最適化しても 5〜10秒程度しか縮まない。

## v1.5 で踏み込むべき場所

### 1. まず profile を取る(必須、推測ベースで最適化しない)

Instruments で実機 export を計測する:

```bash
xcrun xctrace record \
  --device 3A2A3A66-D092-5F87-8CE7-9A1EBD238FE9 \
  --template 'Time Profiler' \
  --launch -- /private/var/containers/Bundle/Application/<UUID>/App.app \
  --time-limit 200s
```

または `os_signpost` を `FilmtoneExportSession.exportVideo` の各 stage に挿入(decode / orient / colorPipeline / writer.append / etc.)→ Instruments の os_signpost lane で stage 別 ms を可視化。

候補 stage(`apps/capacitor-film-lab-ios/ios/App/App/FilmtoneExportSession.swift` 内):

- `videoOutput.copyNextSampleBuffer()` → decode
- `orientAndScale(...)` → CIImage transform(CIContext.render とは別)
- `colorPipeline.process(image:...)` → 主たる grade 計算
- `applyGlowFamilyStage(...)` → bloom/halation/diffusion(MIP chain で重い)
- `applyDepthPrefilter(...)` → depth-coupled glow(depth on のみ)
- `adaptor.append(rendered, withPresentationTime:)` → encode / writer

### 2. 高コスト stage の Metal 化検討

CIContext.render は同期で stage 間で frame 単位 stall を作る。
具体的には:

- `apps/capacitor-film-lab-ios/ios/App/App/FilmtoneColorPipeline.swift` 内の CIKernel 連鎖
- `FilmtoneRayAngleOptics.swift` の lens-filter optics

検討案:
- (a) CIKernel を MTLComputeCommandEncoder の compute kernel に置き換える
- (b) 連鎖する CIFilter / CIKernel を 1 つの大きな fragment shader に融合(現状はおそらく n 段階の CIImage chain で intermediate buffer が回ってる)
- (c) CIContext を Metal device-backed で再作成(`CIContext(mtlDevice: ...)`、現状は default — 確認要)

### 3. Pipeline 並列化

現状の AVAssetReader → CIContext.render → AVAssetWriterInput.append は決して fully-parallel ではない。
特に CIContext.render は同期で main pump を block する。
解決案:

- 3-stage triple-buffering: decode → render → encode を独立 dispatch queue で動かし、frame slot を ring buffer で受け渡す
- `videoInput.requestMediaDataWhenReady(on:)` の queue を複数にして frame 単位で並列実行(順序は presentationTime で writer 側が直列化)

### 4. VideoToolbox 直結による decode + 直接 CVPixelBuffer 回し

`AVAssetReaderTrackOutput` は内部で VideoToolbox 経由で decode してる(BGRA を要求するとそれに変換される)。
HDR 経路では既に `420YpCbCr10BiPlanarVideoRange` で読んでいる。
→ もし内部変換コストが見えるなら `VTDecompressionSession` を直接駆動して outputCallback で CVPixelBuffer を CIImage に投入し、無駄な copy/format conv を消す余地がある。ただし複雑さに見合うかは profile 結果次第。

### 5. 出力解像度ベースのキャッシュ戦略再考(v1.4 で disable した Quality mezzanine の再有効化)

仮に grade pipeline が高速化されると decode の相対重要度が上がる。
そのとき有効な cache 戦略:

- 1080p HEVC Main10 25Mbps(現状の preview-grade `hdr` profile と同等)を Quality export でも使う
- `FilmtoneMezzanineRoutePolicy.qualityVariantPreference` を変えて Quality 経路でも `.hdr` cache を流用
- ただしこれは Profile.version の互換性検討が必要(現状 Quality 系列は別 schema variant)

優先度: profile 結果 → 高速化方針確定 → 必要なら cache 戦略。最初に飛びつかない。
