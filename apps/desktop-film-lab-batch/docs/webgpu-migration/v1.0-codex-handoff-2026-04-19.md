## 5. What the 2026-04-19 follow-up changed

This section describes the code added in the latest follow-up work.

### 5.1 Renderer-native WebGPU readback was added

Files:

- `packages/film-lab-renderer/src/Viewport.ts`
- `packages/film-lab-renderer/src/webgpu/WebGPUBackend.ts`
- `apps/desktop-film-lab-batch/src/renderer/offscreen/webgpu-offscreen-render-session.ts`
- `apps/desktop-film-lab-batch/src/renderer/offscreen/webgpu-offscreen-render-session.test.ts`
- `apps/desktop-film-lab-batch/src/renderer/offscreen/offscreen-render-session.ts`

What changed:

- `Viewport` gained:
  - `setReadbackEnabled(enabled: boolean)`
  - `readbackRgba8(): Promise<Uint8Array>`
- `WebGPUBackend` gained:
  - opt-in readback enablement
  - a copyable readback target (`rt.present.readback`)
  - GPU staging buffer allocation / reuse
  - `copyTextureToBuffer` readback
  - row de-padding for 256-byte `bytesPerRow` alignment
  - bottom-up RGBA output normalization so the existing video export raw-frame
    contract remains unchanged
- `webgpu-offscreen-render-session.ts` no longer performs
  `canvas -> 2D -> getImageData`
- instead it enables renderer readback and delegates to
  `viewport.readbackRgba8()`

### 5.2 Important implementation detail of the new readback path

The new WebGPU readback path does **not** read from the linear HDR
`rt.composited` texture.

It mirrors the **final present pass** into an additional
`rgba8unorm-srgb` readback target and then reads that target back.

This was done intentionally so that:

- readback matches the post-composite final display stage rather than a
  pre-display intermediate,
- hardware linear -> sRGB output transform stays aligned with the preview path,
- video export receives bytes that are closer to the actual presented image.

### 5.3 What was intentionally not changed

The following was **not** changed in the 2026-04-19 follow-up:

- batch export still encodes through:
  `canvas.toDataURL(...) -> fetch(dataUrl) -> Uint8Array`
- no attempt was made yet to replace batch encode/write with a true
  readback-driven PNG/JPEG path
- no attempt was made yet to remove the old intra-backend fallback concepts in
  video export

This was intentional because the critical-path work was fixing the WebGPU
readback seam first, not broad cleanup.

## 8. Current investigation status of the manual QA failures

The chat was interrupted while investigating these three issues.

The next agent should treat the analysis below as the latest state of
understanding.

### 8.1 Verified fact: WebGPU composite shader still omits lens softness and aberration edge soften

This is a high-confidence finding from direct code inspection.

In:

- `packages/film-lab-renderer/src/webgpu/shaders/composite.frag.wgsl.ts`

the file explicitly says these are deferred:

- `lens softness blur`
- `aberration edge soften`

The relevant lines are the comment block at the top of the WGSL composite
shader.

In contrast, the WebGL composite shader **does** implement both:

- `packages/film-lab-renderer/src/webgl/shaders/composite.frag.ts`

contains:

- edge mask and lens softness weight
- `uLensSoftness`
- `uAberrationEdgeSoften`
- 8-tap blur mix

Implication:

- the user-reported "lens softness is much less effective" is very likely a
  real, pre-existing WebGPU parity gap,
- not merely a side effect of the new readback path.

### 8.2 Verified fact: WebGPU grain model is intentionally different from WebGL grain

This is also a high-confidence finding from direct code inspection.

WebGPU grain:

- `packages/film-lab-renderer/src/webgpu/shaders/composite.frag.wgsl.ts`

uses:

- repeated blue-noise tile sampling
- single-channel grain sample
- radial weighting

WebGL grain:

- `packages/film-lab-renderer/src/webgl/shaders/composite.frag.ts`

uses:

- per-pixel hash
- time-stepped grain frame
- per-channel chroma/luma grain separation
- low-frequency clump noise / density modulation

Implication:

- the user-reported "film grain quality became worse" is consistent with a
  real WebGPU preview/export parity gap,
- not necessarily with a regression in `copyTextureToBuffer` readback itself.

### 8.3 Unresolved: upside-down light bleed / halation orientation

This issue was **not** resolved before the chat ended.

Current state:

- no confirmed root cause yet
- investigation was in progress

The leading suspects at interruption time were:

1. orientation interplay in the WebGPU source upload / fullscreen path:
   - `packages/film-lab-renderer/src/webgpu/MediaTexture.ts`
   - upload uses `flipY: true`
   - the fullscreen vertex shader also has an export-time `flipY` flag
2. row-order normalization inside the new WebGPU readback path
3. ffmpeg row-order handling in video export:
   - `apps/desktop-film-lab-batch/electron/main.ts`
   - existing `vflip` assumption still exists
4. possible mismatch between preview path and offscreen export path in how
   halation textures are sampled or mirrored

What is **not** yet known:

- whether the upside-down glow issue happens in:
  - batch export only
  - video export only
  - both
- whether the whole frame is inverted or only the glow/halation contribution is
  inverted relative to the base image
- whether the issue reproduces in WebGPU preview itself, or only in export

This needs targeted investigation, not assumption.
