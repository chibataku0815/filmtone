## 4. 本 chat で決着した技術判断

### 4-1. FilmLabCanvas WebGPU 分岐の実装方針(commit `c1987104`)

**問題**: 元コードは `renderer = new THREE.WebGLRenderer()` が先に canvas を作り WebGL2 context を張ってしまうので、`canvas.getContext('webgpu')` は null を返す。WebGPU は **fresh canvas**(まだ context を張っていない canvas)が必須。

**採用した順序**:
1. `document.createElement("canvas")` → `canvasRef` に保持、container に append(style は 100% width/height、display: block)
2. 環境変数 `FILMTONE_BACKEND` を `import.meta.env` から read(desktop = `"webgpu"`、web = `"webgl"`、vite build flag で注入、無ければ `"webgl"` default)
3. 非同期 IIFE 内で `isWebGPUSupported()` を await → `webgpu-desired AND supported` で `effectivePref = "webgpu"`、それ以外は `"webgl"`
4. `await Viewport.create(canvas, { prefer: effectivePref, width, height })` — backend 決定は Viewport 側でさらに内部フォールバックを含む
5. `vp.backendKind === 'webgl'` なら `new THREE.WebGLRenderer({ canvas, antialias:false, alpha:false, preserveDrawingBuffer:true })` を同じ canvas で作る(THREE は `canvas:` option で既存 canvas を掴む)+ scene / camera / mesh / `webglcontextlost` listener を wire
6. `vp.backendKind === 'webgpu'` なら THREE の初期化を全て skip + `await vp.prewarm()` で pipeline JIT 予熱
7. animate loop は `renderer && scene && camera` の存在で分岐(`viewport.render(renderer, scene, camera)` vs `viewport.render()`)

**backend-agnostic 化した API 面**:
- `handleDownload` → `canvasRef.current.toDataURL('image/png')` 直読み
- `getJpegBase64ForAi` → 同上
- `getWebGlCanvas` → `canvasRef.current`(名前は WebGL だが戻り値は両 backend の canvas)
- `getPreviewHealth.hasRenderer` → `viewportRef && canvasRef` の両方の存在で判定(WebGPU では renderer 無しでも preview alive)
- `replaceSourceFromPngBase64Body` / `restoreCurrentSource` → renderer.capabilities.maxTextureSize が取れないケース(WebGPU)は `getMaxTextureSize()` helper で 8192 フォールバック

**破壊していない箇所**:
- `FilmLabCanvasProps` / `FilmLabCanvasRef` 型は完全に同じ
- 既存 consumer(apps/web / batch-pipeline / video-export-pipeline)は無変更
- WebGL path の挙動は before/after で一致

**既知の型警告**:
- `import.meta.env.FILMTONE_BACKEND` の型が `ImportMetaEnv` にないため `(import.meta.env ?? {}) as unknown as Record<string, unknown>` 経由で読む
- `(import.meta.env.BASE_URL)` はこのファイルの既存 pre-existing error(TS2339)→ 触らない、baseline の一部

### 4-2. video export / batch export は WebGL 固定(D5 路線に沿う再確認)

`apps/desktop-film-lab-batch/src/renderer/video-export-pipeline.ts:1031` と `batch-pipeline.ts:395` で `Viewport.create(renderer.domElement, { prefer: 'webgl', ... })` と明示されていることを本 chat で確認済み。

**帰結**: v1.0 は **preview だけ WebGPU**、**export は WebGL**。shader と LUT は同一経路なので通常色域では同じ出力になるが、rgba16float no-clamp(WebGPU)と rgba8 clamp(WebGL)が highlight 1.0+ で理論上乖離する。これが **v1.0 最大の user-visible リスク**。

### 7-b. Step 3 で highlight のみ乖離 → 方針判断

- **選択肢 A**: v1.0 の preview で clamp 追加(色が浅くなるが preview = export を保証)— 色品質という v1.0 の売りが弱まる
- **選択肢 B**: v1.1 で video-export を WebGPU にするまで v1.0 を hold — リリース遅延
- **選択肢 C**: release notes に明示して ship(ユーザー教育)— 初物の受容度次第

→ direction chat へ escalate、DIRECTION §9 "色空間パラダイム変更" 相当の strategic 論点

### 7-c. Step 3 で全体トーン乖離

想定外。原因候補:
- soft-shaper の係数(k=0.5)が export 側で効いていない
- LUT2 の binding が WebGPU と WebGL で違う
- sRGB OETF が二重掛かりしている
→ hold + 調査 issue 起票、direction chat でチケット化

### 7-d. Step 2 で動画が動かない

原因は FilmLabCanvas の新 setTexture 経路が高確率:
- `packages/film-lab-renderer/src/Viewport.ts:326` `queueSetTextureWebGPU`
- `generation` counter が stale 判定で bitmap を早期破棄している可能性
- `createImageBitmap(HTMLVideoElement)` が再生中に失敗する可能性(codec / CORS)
- `MediaTexture.setFromBitmap` で format 不整合

デバッグ手順:
1. DevTools で `queueSetTextureWebGPU` に `console.log` を挿入、generation と bitmap 生成の成否を追う
2. 再生中に `viewport.setTexture` がどのくらいの頻度で呼ばれているか確認
3. 頻度高すぎで race している場合は debounce or rAF sync

### 7-e. 起動時に WebGPU fallback

DevTools Console に `[Viewport] WebGPU backend bootstrap failed — falling back to WebGL` が出た場合:
- macOS version / Electron version / WebGPU feature availability を確認
- Phase 0 Case A(`apple`/`metal-3`)の adapter info との差分を確認
- 必要なら DIRECTION §9 "Case C(WebGPU 完全非対応環境)" 判定 → 計画全体見直し or v1.0 を "internally WebGPU but fallback to WebGL" として ship
