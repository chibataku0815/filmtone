### 3.2 `ca5de309` — composite parity: glow orientation, grain, lens softness (port)

Fixed the three QA findings that the 2026-04-19 pre-parity handoff
reported. All changes live in `composite.frag.wgsl.ts` +
`compositeUniforms.ts`. No pipeline layout change.

#### 3.2.1 Glow orientation fix (bloom / halation were upside-down)

Root cause: the procedural fullscreen vertex shader derives
`uvRaw.y = y * 0.5 + 0.5`, and WebGPU texture sampling has
(0,0)=top-left, so sampling `uv.y = 1` reads the bottom texture row.
The net effect is that each fullscreen render pass flips the sampled
content vertically relative to the framebuffer. The base path goes
through an EVEN number of such passes on the way to the swap chain
(media upload flip + filmlab + composite + blit); the bloom / halation
path goes through ONE additional pass (the prefilter) on top of that,
so at composite-read time bloom/halation are stored inverted along y
relative to `rtColorGraded`.

The minimal fix: in the composite fragment shader, sample `uBloom` and
`uHalation` at `vec2f(uv.x, 1.0 - uv.y)` so the glow lookup compensates
for the extra flip and aligns with the base. This avoids touching the
pyramid chain, `MediaTexture.flipY`, or the vertex shader.

User QA after the fix confirmed glow orientation appears correct.
(The user's latest feedback is about intensity, not orientation.)

#### 3.2.2 Grain parity port

Replaced the blue-noise tile model with the WebGL silver-halide grain
model 1:1:

- per-pixel `sin/fract` hash seeded by absolute pixel coord + per
  channel seeds for chroma/luma separation,
- low-frequency clump noise (`valueNoise`) modulating grain density,
  keyed by `grainSize`,
- 3 Hz temporal stepping (`floor(time * 3)`),
- radial weight envelope retained for parity with the WebGL path.

Legacy `uGrain` / `uGrainSampler` bindings are left declared with a
zero-weight contribution so the pipeline bind-group layout stays
unchanged.

User QA after the fix: not explicitly re-reported, but not called out
as a regression. Treat as provisionally OK until the user re-asserts.

#### 3.2.3 Lens softness + aberration edge-soften port

Ported the WebGL 8-tap cross+diagonal blur path:

- edge mask `smoothstep(0.25, 1.0, length(edgeDelta) * 1.414)`
- `lensW = pow(lensR, 1.52)` with `lensR = clamp(length(edgeDelta)*2, 0, 1)`
- `lensDrive = pow(lensSoftness, 0.78)` (γ < 1 for visibility)
- `lensWeight = lensDrive * lensW`
- `blurRadiusPx = mix(1.5, 2.75, aberrationEdgeSoften) + lensWeight * 1.35`,
  clamped to 4.2 px
- 8-tap cross + diagonal blur of `uSource` with that radius
- `softenAmt = clamp(aberrationEdgeSoften * edgeMask + lensMix * edgeMask, 0, 1)`
  where `lensMix = lensWeight * 0.72`
- `color = mix(sharpRgb, blurRgb, softenAmt)`

Required extending the composite uniform struct with a fourth vec4
`lens = (lensSoftness, aberrationEdgeSoften, _, _)`. `COMPOSITE_UNIFORM_FLOATS`
went 12 → 16. The packer reads `state.params["lensSoftness"]` and
`state.params["aberrationEdgeSoften"]` directly.

**This is where the NEW regression lives** — see §5.

### 5.1 Lens softness feels weak — root-cause candidate: `aberrationEdgeSoften` is never fed to the WebGPU path

Finding, verified by direct code inspection:

- The WebGL backend derives `uAberrationEdgeSoften` as a function of
  `rgbShift`:
  ```ts
  // packages/film-lab-renderer/src/webgl/WebGLBackend.ts:143
  const ABERRATION_EDGE_SOFTEN_SCALE = 32;
  // packages/film-lab-renderer/src/webgl/WebGLBackend.ts:926-929
  cu.uAberrationEdgeSoften!.value = Math.min(
    1,
    Math.max(0, rgbShift * ABERRATION_EDGE_SOFTEN_SCALE),
  );
  ```
- There is NO user-facing `aberrationEdgeSoften` slider. The only
  upstream input is `rgbShift`.
- `packCompositeUniforms` in WebGPU reads
  `state.params["aberrationEdgeSoften"]` directly, which is never set by
  the UI or by the WebGPU backend. It falls back to `0`.
- Therefore in the WebGPU preview, even when `rgbShift > 0`,
  `aberrationEdgeSoften` is always `0`.

Impact on the visible lens softness:

- `blurRadiusPx = mix(1.5, 2.75, aberrationEdgeSoften) + lensWeight * 1.35`
  → in WebGPU, this is `1.5 + lensWeight * 1.35`, capped 4.2
  → with `rgbShift > 0` in WebGL this is `≈ 2.75 + lensWeight * 1.35`
     because `aberrationEdgeSoften` saturates to 1.
- `softenAmt = clamp(aberrationEdgeSoften * edgeMask + lensMix * edgeMask, 0, 1)`
  → in WebGPU this is `0 + 0.72 * lensWeight * edgeMask`, max 0.72
  → in WebGL with `rgbShift > 0` this is `edgeMask + 0.72 * lensWeight * edgeMask`,
     clamped to 1 → fully saturated blur mix at periphery.

Consequence: the WebGL preview fully swaps to the blurred sample at
the periphery when both `rgbShift` and `lensSoftness` are up. The
WebGPU preview tops out at a 72 % mix, with a smaller blur radius.
That is exactly the "feels weak" symptom the user reported.

Recommended fix (for the next chat):

- In `packCompositeUniforms` (or in `WebGPUBackend.uploadFrameUniforms`
  just before packing), derive `aberrationEdgeSoften` from
  `params["rgbShift"]` the same way WebGL does:
  ```ts
  const ABERRATION_EDGE_SOFTEN_SCALE = 32;
  const rgbShift = typeof params["rgbShift"] === "number"
    ? (params["rgbShift"] as number)
    : 0;
  out[13] = Math.min(1, Math.max(0, rgbShift * ABERRATION_EDGE_SOFTEN_SCALE));
  ```
  Keep `lensSoftness` reading direct from `params["lensSoftness"]`.
- Alternative: keep packer as-is and derive in the shader — but that
  couples shader math to a UI-facing param name; packer is cleaner.
- After the fix, headless verify and ask for a short manual QA pass.

### 5.2 Light diffusion feels weak — root cause: the `diffusion` effect is not ported to WebGPU at all

Finding, verified by direct code inspection:

- The UI exposes a user-facing `diffusion` slider (Pro-Mist / Cinebloom
  light scattering).
  - `packages/film-lab-ui/src/FilmLabControlPanelCore.tsx:972-978`
    renders the slider and dispatches `updateParam("diffusion", v)`.
  - Presets set non-zero defaults (e.g. `0.08`, `0.16`).
- The WebGL backend maintains a separate pyramid `rtDiffusionMips` and
  a `uDiffusionTexture` sampler, used inside
  `packages/film-lab-renderer/src/webgl/shaders/composite.frag.ts`:
  ```glsl
  if (uDiffusion > 0.0) {
    vec3 diffused = texture(uDiffusionTexture, vUv).rgb;
    vec3 diffOpacity = glowShoulder(diffused * uDiffusion * 0.29)
                     * glowHeadroom(baseRgb, 0.88);
    vec3 diffScreen = 1.0 - (1.0 - color.rgb) * (1.0 - diffOpacity);
    color.rgb = diffScreen;
  }
  ```
- The WebGPU composite shader explicitly lists `diffusion` as deferred
  in its header comment, and there is no WGSL diffusion prefilter,
  pyramid, or sampler binding. The v1.0 audit also calls this out as
  a P1-adjacent "未接続" effect.

Consequence: the user moves the `diffusion` slider in the WebGPU
preview, but nothing happens — the shader simply has no path for it.

Recommended fix (for the next chat), in order of increasing
invasiveness:

1. **Quick placebo option (do NOT ship)**: a 1-tap full-image screen
   blend using the existing `bloom` or `halation` pyramid at a scaled
   strength. This is NOT parity — it ignores the "all light, not just
   highlights" property of diffusion — and the user will notice, so
   skip.
2. **Minimum-parity port**: introduce a third pyramid chain
   `rtDiffusion` with its own prefilter (one that passes through the
   full image rather than gating on luma — essentially a straight
   downsample/upsample blur). Add a 4th bloom-like texture binding to
   the composite bind group. Match the WebGL `0.29` multiplier and the
   `glowHeadroom(..., 0.88)` value.
3. **Stretch**: instead of a fresh pyramid, reuse the existing bloom
   pyramid with the prefilter switched to a luma-neutral identity
   when `diffusion > 0`. Lower memory footprint but entangles two
   effects; not recommended.

Option (2) is the recommended scope for the first pass.
