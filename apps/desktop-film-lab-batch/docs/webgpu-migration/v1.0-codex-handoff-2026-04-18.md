## 2. Original user intent and plan of record

The user provided a two-stage plan and asked that it be implemented.

### M1: Preview parity stabilization

Required outcomes:

- Introduce an explicit renderer contract with capability reporting and
  context-loss reporting.
- Split WebGPU live video upload from one-shot bitmap upload.
- Make split state round-trip correctly on WebGPU.
- Surface fatal prewarm/render/device-loss failures into preview lifecycle.
- Capability-gate unsupported WebGPU UI instead of showing inert controls.
- Convert export-after-preview recovery to awaitable recovery logic.
- Update docs / release framing so v1.x is described as
  "WebGPU preview with gated unsupported features", not full parity.

### M2: Export convergence

Required outcomes:

- Introduce backend-neutral offscreen render session seams.
- Extract shared grade / LUT application.
- Migrate batch export first.
- Migrate video export second.
- Eventually add WebGPU offscreen implementation and swap backend in the same
  `batch -> video` order.

### Explicit non-goals from the user plan

- Do not switch desktop default back to WebGL.
- Do not reintroduce silent fallback.
- Do not leave compare / histogram visible but non-functional on WebGPU.
- Do not require compare parity to be complete in M1.

### 5.2 What the uncommitted checkpoint does

#### A. Offscreen session contract evolved

`offscreen-render-session.ts` now includes:

- `prefer?: "webgl" | "webgpu"`
- `setSource(...)` can be async
- `readbackRgba8(): Uint8Array | Promise<Uint8Array>`

This is the minimum needed to support async WebGPU source upload and
backend-neutral frame readback.

#### B. Explicit backend selection helper added

`create-offscreen-render-session.ts` now exists.

Current behavior:

- `prefer: "webgl"` -> create WebGL session
- otherwise -> create WebGPU session
- default is `webgpu`
- there is no `auto`
- there is no fallback

Current implementation:

```ts
const { prefer = "webgpu", ...sessionOptions } = options;
if (prefer === "webgl") return createWebGLOffscreenRenderSession(sessionOptions);
return createWebGPUOffscreenRenderSession(sessionOptions);
```

#### C. WebGPU offscreen session exists now

`webgpu-offscreen-render-session.ts` now exists.

Current behavior:

- Creates a fresh canvas
- Creates a `Viewport` with `prefer: "webgpu"`
- Accepts source textures via:
  - direct `viewport.setTexture(...)` for live `HTMLVideoElement`
  - direct `viewport.setMediaFromBitmap(...)` for `ImageBitmap`
  - `createImageBitmap(...)` upload for other canvas-image sources
- Applies grade via shared helper
- Renders via `viewport.render()`
- Enables backend-native viewport readback
- Reads back RGBA via renderer-level WebGPU readback

Current implementation details:

- `Viewport` now exposes opt-in WebGPU readback controls for this offscreen use
  case only.
- `WebGPUBackend` mirrors the final present pass into a copyable
  `rgba8unorm-srgb` readback target when readback is enabled.
- `readbackRgba8()` now uses `copyTextureToBuffer`, strips 256-byte row
  padding, and returns bottom-up RGBA8 so the existing video-export raw-frame
  contract remains unchanged.

Important limitation:

- This is now backend-native readback, but it is still not manually verified on
  a real desktop machine in this chat.
- The duplicated final present pass may have performance cost that tests will
  not reveal.

#### D. Batch export now targets explicit WebGPU offscreen

`batch-pipeline.ts` now:

- uses `createOffscreenRenderSession({ prefer: "webgpu" })`
- awaits `renderSession.setSource(...)`
- logs the chosen backend

Current behavior:

- It still encodes via `canvas.toDataURL(...)`, then `fetch(dataUrl)`,
  then writes output bytes through `api.writeOutputFile(...)`.
- It is therefore not yet using `readbackRgba8()` for image encoding.
- That is acceptable as a temporary checkpoint, but it means batch export is
  not yet fully converted to a readback-driven backend-neutral path.

#### E. Video export now attempts explicit WebGPU offscreen

`video-export-pipeline.ts` now:

- creates the render session via:
  `createOffscreenRenderSession({ prefer: "webgpu", ... })`
- awaits async `setSource(...)`
- logs the chosen backend
- uses:
  - existing WebGL PBO readback path when backend is WebGL
  - session `readbackRgba8()` when backend is WebGPU

This means:

- the code path has been prepared for WebGPU offscreen export,
- and WebGPU readback no longer depends on `canvas -> 2D` bridging,
- but it has not yet been manually verified on a real machine in this chat.

## 8. Current open questions / risks

### 8.1 WebGPU readback is now renderer-native but still unverified on hardware

Current implementation:

- final present pass is mirrored into a copyable WebGPU texture
- readback uses `copyTextureToBuffer`
- the staging buffer rows are de-padded and normalized to bottom-up RGBA8

Why this is risky:

- Even though this is backend-native now, it still changes the final present
  path by rendering the last pass twice when readback is enabled.
- The row-order contract is intentionally preserved for video export, but that
  needs real ffmpeg verification on desktop.
- Tests do not tell us whether platform-specific WebGPU / Metal drivers behave
  correctly under this copy path.

Recommended follow-up:

- run real desktop QA first
- if stable, keep this as the checkpoint and decide later whether to optimize
  the duplicated present pass

### 8.2 Batch export is still encoded through `toDataURL`

Even though WebGPU offscreen is now selected explicitly, batch export still:

- renders,
- calls `toDataURL(...)`,
- fetches the data URL back into bytes,
- then writes bytes.

That means:

- the rendering backend has moved,
- but the encode/write leg is still canvas-string-based,
- and `readbackRgba8()` is not yet driving batch image encoding.

That is fine as an incremental checkpoint, but not the cleanest final state.

### 8.3 Video export still contains old intra-backend fallbacks

These are still present:

- WebCodecs runtime retry to HTMLVideoElement seek path
- WebGL PBO path falling back to sync `readPixels`

Those are not backend fallbacks, but they are still fallback logic.

If the user wants *all* fallback classes removed, that remains future work.
